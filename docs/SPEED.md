# Как ускорить генерацию токенов: что реально работает, а что миф

Коротко: «в несколько раз быстрее» на телефоне достигается **не** заменой языка
на Rust и не одним трюком, а комбинацией. Ниже — по убыванию эффекта, с оценками
для типичного Snapdragon 7-8 gen / Dimensity и модели 0.5–3B Q4_K_M.

| Техника | Что даёт | Где в проекте |
|---|---|---|
| **KV-cache prefix reuse** (не пересчитывать историю) | 2–50x к времени до первого токена на длинных чатах | `crates/turbollm-core/src/session.rs` |
| **Speculative decoding / MTP** (draft-модель или MTP-голова) | 1.8–3x токенов/с при той же точности | `docs/SPEED.md` §3, `speculative` в `llama-cpp-2` |
| **Квантование** Q4_K_M + KV-кэш q8_0 | 1.5–2x (меньше памяти → больше влезает в кэш CPU) | `LoadOptions::kv_type` |
| **Flash attention** | 1.2–1.6x на длинном контексте | `LoadOptions::flash_attn` |
| **Треды по big-ядрам** (`n_threads = big_cores`) | 1.2–1.5x vs «все ядра» | `Settings.nThreads()` |
| **LTO + codegen-units=1 + `-march=armv8.2-a+dotprod+i8mm`** | 1.1–1.3x | `Cargo.toml`, `cargo-ndk` |
| **GPU-бэкенд** (OpenCL/Vulkan, Adreno/Mali) | 1.5–4x для больших моделей, но +батарея | feature `opencl`/`vulkan` |
| **Rust вместо Kotlin/Java в горячем цикле** | ~0 (сэмплинг — это доли процента) | — |

Что **не** ускоряет генерацию, хотя часто упоминается:

* переписывание UI/логики на Rust;
* `torch.compile`/ONNX Runtime на Android для LLM (нет поддержки квантованных
  GGUF-ядер и групповых matmul так, как в GGML);
* 「ускорители» вроде `llm-rs`/`candle` на телефоне: candle хорош для эмбеддингов
  и маленьких моделей, но на токен/сек обычно проигрывает GGML с NEON-dotprod.

---

## 1. KV-cache reuse — самый большой практический выигрыш

Наивное приложение на каждый вопрос прогоняет через модель **весь** диалог:

```
ход 5, история 3000 токенов, prefill 60 tok/s  ->  50 секунд ожидания
```

Наш `ChatSession` держит `Vec<LlamaToken>` того, что уже лежит в KV-кэше, и
инкрементально декодирует только новый суффикс:

```
ход 5 -> decode 80 новых токенов -> 1.3 секунды
```

Замер на этом проекте (x86_64, 2 потока, Qwen2.5-0.5B Q4_K_M, 6 ходов,
`cargo run --bin turbollm-bench -- --compare`):

```
prefill of 6 turns: naive 7475 ms vs KV-reuse 2914 ms => 2.56x faster
```

На телефоне с историей 4k токенов и 5–7B моделью выигрыш доходит до 20–50x,
потому что prefill на ARM в 5–10 раз медленнее десктопа, а decode — нет.

Как это устроено:

1. рендерим историю шаблоном чата → строка;
2. токенизируем, ищем длину общего префикса с `session.cached`;
3. если префикс короче — `kv_cache_seq_rm(0, common, None)` (пользователь
   отредактировал сообщение);
4. декодируем только `tokens[common..]` батчами по `n_batch`;
5. сгенерированные токены дописываем в `session.cached`, чтобы следующий ход
   не перечитывал даже ответ ассистента;
6. если контекст переполняется — сдвигаем окно (`kv_cache_seq_rm(0,0,drop)`) и
   увеличиваем `n_past_trimmed`, чтобы позиции RoPE оставались монотонными.

## 2. Почему Rust, а не «просто Kotlin»

Сама генерация живёт в C++ (llama.cpp/GGML), поэтому «язык» сам по себе
скорость не меняет. Rust даёт другое:

* **нет GC-пауз и JNI-моста в горячем цикле** — токены отдаются колбэком
  один раз на токен, а не через `String`-аллокации на каждый шаг;
* `staticlib`/`cdylib` собирается тем же `cargo` в CI, с `lto=fat` и
  `-C target-cpu` под ARM, без Gradle-магии и CMake-обвязки на стороне app;
* одна и та же логика запускается на хосте (`turbollm-bench`) — бенчмарк в CI
  проверяет движок на каждом коммите;
* безопасные обёртки (`llama-cpp-2`) не дают случайно перепутать порядок
  `llama_decode`/`llama_sampler_accept`, который в C-примерах — источник багов.

## 3. Speculative decoding: единственный способ получить «в разы» на токенах

Decode — это memory-bound: каждое следующее слово требует чтения всех весов
модели. Поэтому «ускорить в 3 раза» математикой нельзя, а «угадать» — можно:

1. **Draft-модель** (0.5B рядом с 7B): драфтер генерирует 4–8 токенов, целевая
   модель проверяет их одним батчем. Принимается в среднем 60–80% → 1.8–2.5x.
2. **MTP / Medusa-головы** (Qwen3-Next, DeepSeek-V3): модель сама предсказывает
   несколько токенов вперёд, без второй модели → 1.5–2x, памяти почти не тратит.
3. **Self-speculation** (prompt lookup / n-gram): дёшево, помогает на
   шаблонных ответах (код, списки, форматирование) — 1.2–1.5x.

В `llama-cpp-2` 0.1.161 есть готовый wrapper `speculative::MtpSpeculative`
(включается фичей `common`) и `llama_rs_mtp_speculative_*` в sys-крейте.
Как включить draft-модель в TurboLLM:

```rust
// pseudo-code, следующий шаг проекта (интерфейс уже заложен: GenParams::use_speculative)
let draft = LlamaModel::load_from_file(&backend, draft_path, &params)?;
let draft_ctx = draft.new_context(&backend, ctx_params.with_n_ctx(Some(512.try_into()?)))?;
let mut mtp = MtpSpeculative::new(target_ctx, draft_ctx, MtpSpeculativeParams {
    n_max: params.draft_tokens, n_min: 1, p_min: 0.1,
})?;
```

Важно: draft-модель должна иметь **тот же токенизатор**, иначе accept-rate падает
до нуля. Пары, которые работают: Qwen2.5-0.5B + Qwen2.5-3B/7B, Llama-3.2-1B +
Llama-3.1-8B.

## 4. Настройки, которые чаще всего «ломают» скорость на телефоне

| Настройка | Как надо |
|---|---|
| `n_threads` | по числу **больших** ядер (обычно 4–6), а не `availableProcessors()` |
| `n_ctx` | ровно столько, сколько нужно (2048/4096), каждый лишний токен = KV-кэш в RAM |
| KV-кэш | `q8_0` (по умолчанию) или `q4_0` для 3B+ моделей |
| `n_batch` | 256–512; больше — не быстрее на ARM, но больше памяти под compute-буфер |
| mmap | **вкл** — иначе Android убьёт процесс при нехватке RAM |
| `n_gpu_layers` | 0 для CPU-сборки; для OpenCL/Vulkan сборки — 99 |
| Модель | Q4_K_M — лучший баланс; IQ3_XXS/IQ4_XS для 6–8 ГБ RAM |

## 5. Как измерить, а не поверить

```bash
# на хосте (x86_64), сравнение с наивным движком
cargo run --release --no-default-features --bin turbollm-bench -- \
    --model model.gguf --tokens 128 --turns 6 --ctx 4096 --compare

# на телефоне: кнопка «Бенчмарк» в настройках приложения
# (или через adb)
adb shell am start -n ai.turbollm.app/.MainActivity
```

Метрики, которые приложение показывает под каждым ответом:
`tok/s`, `TTFT` (время до первого токена), `из кэша N/M токенов`, `prefill tok/s`.
