# Архитектура

```
┌─────────────────────────────── Android app (Java, без AndroidX) ───────────┐
│ MainActivity ── чат, стриминг в TextView, настройки, бенчмарк              │
│ NativeBridge ── JNI-фасад: handle'ы long, JSON-ошибки, JSON-параметры      │
│ Settings     ── SharedPreferences, поиск *.gguf на устройстве              │
│ InferenceService ── foreground-сервис, чтобы процесс не замораживали       │
└───────────────────────────────┬────────────────────────────────────────────┘
                                │ JNI (libturbollm_core.so)
┌───────────────────────────────▼───────────────── Rust core ────────────────┐
│ jni_bridge.rs  — преобразование JNI <-> Rust, ловля паник, LastError       │
│ Engine         — LlamaModel + LlamaContext (Mutex), mmap, flash attn,      │
│                  KV-кэш q8_0/q4_0, отмена через AtomicBool                 │
│ ChatSession    — chat-template, токенизация, поиск общего префикса,        │
│                  инкрементальный prefill, сэмплер, UTF-8-декодер, stats    │
│ api.rs         — GenParams / GenStats / ChatMessage (serde JSON)           │
└───────────────────────────────┬────────────────────────────────────────────┘
                                │ llama-cpp-2 (safe wrappers) + llama-cpp-sys-2
┌───────────────────────────────▼────────────────────────────────────────────┐
│ llama.cpp / GGML (C++, cmake, NEON/dotprod/i8mm, arm64 + armv7 + x86)      │
└────────────────────────────────────────────────────────────────────────────┘
```

## Потоки данных при генерации

1. UI собирает историю `List<Msg>` → JSON → `nativeGenerate`.
2. `ChatSession::render` вставляет историю в chat-template модели
   (`llama_chat_apply_template`, шаблон из GGUF; fallback — ChatML).
3. Токенизация, поиск `common_prefix` с `session.cached`.
4. `kv_cache_seq_rm(0, common, None)` — если пользователь отредактировал историю.
5. Prefill только `tokens[common..]`, батчами по `n_batch`, logits только на
   последнем токене.
6. Цикл decode: `token_data_array` → sampler chain (penalties → top_k → top_p →
   min_p → temp → dist) → `sample_token`, `accept`, EOG-проверка, UTF-8-декодер
   (не режет многобайтовые символы), колбэк `onToken`, `llama_decode` одного
   токена.
7. Возврат `{"text":…, "stats":{prompt_tokens, cached_tokens, decode_tps,
   prefill_tps, ttft_ms, stop_reason}}`.

## Почему именно так

* **Один Mutex на контекст**: `llama_context` — `Send`, но не `Sync`; Mutex
  делает `Engine` безопасным для JNI без `unsafe impl` в горячем пути.
* **`unsafe transmute` для времени жизни контекста**: `LlamaContext<'model>`
  заимствует модель, а JNI-хэндл должен жить в одной структуре. Поля дропаются
  в порядке объявления, поэтому `ctx` (объявлен первым) умирает раньше `model`.
* **Отмена**: `AtomicBool` проверяется перед каждым токеном — «Стоп» реагирует
  за один шаг (< 100 мс), память не течёт.
* **`OnceLock` для бэкенда**: `llama_backend_init` обязан быть однократным на
  процесс, а JNI-вызовы приходят с разных потоков.
* **Паники не выходят в JVM**: `catch_unwind` в `guard()` + JSON-ошибка,
  иначе Android получит SIGABRT и закроет приложение.

## ABI / упаковка

* `libturbollm_core.so` — `cdylib` из `cargo-ndk`, собрана из Rust-ядра.
  llama.cpp собирается с `android-shared-stdcxx`, поэтому рядом кладётся
  `libc++_shared.so`, скопированный из `sysroot/usr/lib/<triple>/` соответствующего
  NDK (скрипт делает это сам). Версия STL всегда ровно та, что в NDK 27 — иначе
  на устройстве подхватится системная, и `libturbollm_core.so` не загрузится.
* `extractNativeLibs="true"` в манифесте — библиотеки распаковываются при
  установке (не нужен `useLegacyPackaging`-трюк и работает на всех API 26+).
* `minSdk 26` — есть `java.lang.invoke` для лямбд без desugar-костылей; d8 всё
  равно десюгаривает под API < 26 при необходимости.

## Порядок полей в `Engine` — не переставлять

Этот раздел существует потому, что ошибка здесь уже один раз стоила
пользователю «приложение загружает модель, отвечает один раз и закрывается».

```rust
pub struct Engine {
    ctx: LlamaContext<'static>,   // ОБЯЗАТЕЛЬНО объявлен первым
    model: LlamaModel,            // модель — второй
    ...
}
```

Rust дропает поля структуры **в порядке объявления**. Если `model` объявлена
раньше `ctx`, то при выгрузке модели `LlamaModel` освобождается первым, а
`LlamaContext` после него обращается к уже освобождённой памяти весов — это
use-after-free внутри C++, который выглядит как мгновенный SIGSEGV без
Java-исключения и без строчки в логе приложения:

* первый ответ успевает пройти (контекст ещё валиден);
* закрытие чата, повторная загрузка модели или выход из экрана → процесс
  умирает целиком.

Комментарий-предупреждение стоит прямо у полей в `engine.rs`; при рефакторинге
это поле порядка менять нельзя.

## JNI: локальные ссылки в горячем цикле

Каждый `new_string` из `JNIEnv` создаёт локальную ссылку. Таблица локальных
ссылок в JNI рассчитана на ~512 записей, и каждая ссылка живёт до возврата из
нативной функции. При стриминге это означало «одна ссылка на токен»: длинный
ответ (≈512 токенов) переполнял таблицу, и процесс абортировался **посередине
ответа** — без исключения, с записью `JNI ERROR (app bug): local reference
table overflow` в logcat.

Решение в `jni_bridge.rs`: в `on_token` и в `emit` открывается локальный фрейм

```rust
env.with_local_frame(8, || { /* строка + вызов колбэка */ })?;
// или, если нужен ручной контроль:
unsafe { env.push_local_frame(8)? };
...
unsafe { env.pop_local_frame(&JObject::null())? };
```

`pop_local_frame` принимает `&JObject::null()` (а не `()`), и функция
`unsafe` — это не опечатка, а требование API `jni` 0.21.

Правило: **любой JNI-колбэк, вызываемый чаще, чем раз на запрос, обязан жить
внутри локального фрейма.**

## Exit-путь: не отправлять задачи в уже закрытый пул

`MainActivity.onDestroy` останавливает генерацию и ждёт завершения рабочего
потока. Историческая ошибка: после `worker.shutdown()` вызывался
`worker.execute(() -> {})` как «толчок» — `ThreadPoolExecutor` в состоянии
`SHUTDOWN` отвергает задачу `RejectedExecutionException`, и приложение падало
именно в момент выхода с экрана. Сейчас задачи не добавляются: `shutdown()`,
затем `awaitTermination(3s)`; если поток не успел остановиться, нативные
хэндлы сознательно не освобождаются (утечка лучше use-after-free, процесс всё
равно завершается).
