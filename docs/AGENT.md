# Агент: инструменты, ReAct и цикл «до успеха»

Документ описывает, как в TurboLLM устроен агентный режим: где живёт цикл, какие
бывают режимы, как модель вызывает инструменты и что делать, если она ошибается.

## 1. Где что лежит

| Слой | Файл | Ответственность |
|---|---|---|
| Цикл агента | `crates/turbollm-core/src/agent.rs` | режимы `Auto` / `ReAct`, парсинг шагов, бюджет повторов, события |
| Встроенные инструменты | `crates/turbollm-core/src/builtin_tools.rs` | `now`, `calc`, `device_info` — считаются в Rust, без Java |
| Реестр инструментов | `crates/turbollm-core/src/tools.rs` | описания (JSON Schema), вызов, флаг `force_json` |
| MCP-клиент | `crates/turbollm-core/src/mcp.rs` | `initialize` → `tools/list` → `tools/call` по HTTP |
| Плагины | `crates/turbollm-core/src/plugins.rs` | манифест плагина + HTTP-инструменты |
| Мост в Kotlin | `jni_bridge.rs` → `NativeBridge.AgentExec` | вызов Java-инструментов (сеть, файлы, системные API) |
| UI | `MainActivity.java` | чипы инструментов, статистика шагов, чекбокс «ReAct» |

Ключевая идея: **цикл и парсинг — в Rust**, а всё, что требует Android API
(HTTP-плагины, MCP-транспорт, файлы, буфер обмена), — в Kotlin. Rust зовёт Kotlin
через JNI-callback `AgentExec`, получает строку-JSON и продолжает цикл.

## 2. Два режима

Переключатель в UI: «Настройки → ReAct (пошаговый агент)» (`Settings.reactEnabled()`,
ключ `agent_react`). В JSON конфигурации это поле `mode`:

```json
{ "mode": "auto",    "max_steps": 6, "max_consecutive_failures": 2, "force_json": false }
{ "mode": "re_act",  "max_steps": 6, "max_consecutive_failures": 2, "force_json": false }
```

> Внимание при правках кода: `AgentMode` сериализуется с
> `#[serde(rename_all = "snake_case")]`, поэтому значение — **`re_act`**, а не `react`.
> Строка `"react"` не распарсится.

**`auto`** — «нативный» путь. Инструменты передаются модели в шапке системного
промпта, ответ модели ожидается в виде tool-call JSON; при `force_json = true`
генерация ограничивается GBNF-грамматикой, так что мусорный JSON физически
невозможен. Плюс: быстрее и короче (1–2 шага). Минус: маленькие модели (0.5B–3B)
часто не выдают tool-call в нужном формате или «забывают» про инструменты.

**`re_act`** — явный текстовый цикл Thought/Action/Observation. Работает с любой
моделью, которая умеет писать текст, — включая Qwen2.5-0.5B. Грамматика не
навязывается (иначе модель не сможет писать `Thought`), вместо неё используется
`stop = ["\nObservation:"]`, чтобы шаг заканчивался ровно на границе наблюдения.

## 3. Формат ReAct, который парсит Rust

Модель обязана отвечать блоками:

```
Thought: нужно посчитать 123 * 45 + 67
Action: calc
Action Input: {"expr": "123 * 45 + 67"}
```

Приложение подставляет результат и продолжает диалог:

```
Observation: 5602
```

и так до:

```
Thought: результат получен
Final Answer: 5602
```

Промпт с этим форматом и списком инструментов собирается функцией
`react_tools_prompt()`; он же перечисляет имена инструментов и их аргументы.

### Что именно прощает парсер

Маленькие модели почти никогда не соблюдают формат идеально, поэтому
`parse_react()` / `parse_action_input()` терпимы к типичным искажениям:

1. **`Action` важнее `Final Answer` в одном блоке.** Если модель написала
   ответ и тут же вызвала инструмент (классика: «Final Answer: 5508» без
   Observation — то есть выдуманный результат), выигрывает `Action`. Ответ будет
   принят только в следующем шаге, уже после наблюдения.
2. **Двоеточие после метки необязательно** — `Action Input {"expr": 1}` тоже
   разбирается.
3. **Action — только первая строка** после метки. Иначе `Action: calc Action
   Input {...}` в одну строку ломало разбор.
4. **Почти-JSON**: `{expr: 2*3}`, `{expr: "2*3"}`, `{ "expr": 2*3 }` — плоский
   сплиттер по `key : value` на верхнем уровне, без требования кавычек.
5. **Псевдонимы аргументов**: `expr`, `expression`, `arg`, `args`, `input`,
   `query`, `text`, а также объект с единственным полем — всё сводится к одному
   выражению (`find_expr`).
6. **Псевдонимы имён**: `calculator`, `` `now` ``, `calc(...)` — сопоставляются
   с `calc` двусторонним префиксным совпадением (`resolve_tool_name`).

## 4. Философия «работает до успеха»

Требование заказчика: приложение не должно сдаваться после первой неудачной
попытки. Реализовано тремя механизмами:

* **Бюджет повторов** — `AgentConfig.max_consecutive_failures` (по умолчанию 2).
  Если шаг не распарсился или инструмент вернул ошибку, в скретчпад добавляется
  `Observation: ошибка ...` и модели даётся ещё попытка с указанием, что пошло не
  так. Счётчик сбрасывается на каждом успешном шаге.
* **Форс-финал при исчерпании бюджета** — вместо падения приложение добавляет
  инструкцию «инструменты больше недоступны, дай лучший ответ из того, что есть»,
  и модель всё равно отвечает (`Final Answer at exhaustion`). Пользователь всегда
  получает текст, а не пустой экран.
* **Ограничение шагов** — `max_steps` (по умолчанию 6 в UI). Защита от
  бесконечного цикла: модель может «обсуждать» задачу вечно.

Состояние видно в UI: под ответом печатается строка статистики
(`шагов: N · токенов: M · инструментов: K`), а каждый вызов показывается чипом
`calc(...) → 5602`.

## 5. Как добавить новый встроенный инструмент

1. В `builtin_tools.rs` добавьте функцию-исполнитель и запись в реестр:

```rust
ToolSpec {
    name: "weather".into(),
    description: "Текущая погода в городе".into(),
    schema: json!({
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"]
    }),
    force_json: true,
}
```

2. Зарегистрируйте обработчик в `builtin_tools::registry()` — он получает
   `&serde_json::Value` аргументов и возвращает `Result<String, ToolError>`.
3. Добавьте тест в `#[cfg(test)] mod tests` — минимум на успешный вызов и на
   кривые аргументы. Проверка: `cargo test --no-default-features --lib`.
4. Ничего в Java менять не нужно: цикл подхватит инструмент автоматически,
   `react_tools_prompt()` и JSON-схема для грамматики строятся из реестра.

## 6. Как это проверить без телефона

```bash
cd /home/user/turbollm
export CARGO_TARGET_DIR=/home/user/buildtarget
cargo run --release --no-default-features --bin agent-smoke -- /home/user/qwen.gguf react
```

Бинарник `agent-smoke` поднимает реальную модель и печатает каждый шаг
(`Thought` / `Action` / `Observation` / `Final Answer`) плюс статистику
prompt/generated токенов и попаданий в KV-кэш. Ожидаемый результат для
`123 * 45 + 67`:

```
Thought -> Action: calc / Action Input {"arg":"123 * 45 + 67"} -> Observation: 5602 -> Final Answer: 5602
```

Если модель в первом шаге «отвечает» правдоподобным, но неверным числом
(например 5508), это нормально: благодаря приоритету `Action` ответ будет
пересчитан после наблюдения, и в финал уйдёт 5602.

## 7. Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| Модель пишет `Thought`, но не вызывает инструменты | в промпте нет списка инструментов | проверьте, что `collectTools()` вернул непустой массив и `max_steps > 0` |
| `шагов: 6`, ответа нет | `max_steps` исчерпан, форс-финал не сработал | смотрите лог `Agent: step` в logcat |
| Инструмент есть, но «неизвестный инструмент» | имя из модели не совпало | добавьте псевдоним в `resolve_tool_name` |
| Ответ приходит целиком, но без вызова | выбран режим `auto` на слабой модели | включите ReAct |
| Приложение закрывается при выходе из чата | UAF при выгрузке модели | см. `docs/ARCHITECTURE.md`, раздел «Порядок полей в Engine» |
